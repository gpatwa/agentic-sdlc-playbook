Open source · governed multi-agent SDLC

Ship production software with a team of agents—and a human where it matters.

Agentic SDLC is a reusable lifecycle for building software with specialized AI agents. Narrow roles hand off through artefacts, every gate fails closed, and the run pauses for a human at the actions that can’t be undone—from a one-paragraph brief to a shipped slice.

What it is

A control plane, not a coding assistant.

One general agent asked to “build the feature” holds the whole repo in its head and degrades. This is the alternative: a pipeline of narrow agents, each with one job, gated end to end.

24 Narrow roles, not one big agent

Each agent owns one input, one output, one decision—from market researcher to release manager to SRE—and hands off through a written artefact, never a shared context window.

CI Gates that fail closed

Typecheck, tests, build, QA, security. A red gate sends the slice back, never forward. Not a claim: security review blocked a finished slice over a bug it found, and the work went back until it was fixed.

⏸ Human approval is a hard stop

Sending on a user’s behalf, deploying, wiring a real model—the run parks, records an auditable approval, and refuses to infer consent from a thumbs-up.

∑ Every run measures—and budgets—itself

Per-stage traces become a live dashboard: SLOs, DORA, and the outliers a run flags on itself. Cost is checked before each step, not discovered afterwards—over budget, the run degrades or stops and asks.

How to use it

Install the pack. Describe a slice. Watch it run.

You need Node 18+ Claude Code git — and nothing else. The playbook and both reference apps have zero dependencies.

  1. Install into any product repo

    The execution pack generates one Claude Code subagent per role from the briefs, with model routing and least-privilege tools baked in.

    node execution/install.mjs .

  2. Start a slice from one line

    The driving session becomes the orchestrator—it plans the slice and writes a resumable state file.

    /agentic-slice "let users bulk-delete saved items"

  3. It drives the lifecycle—and stops for you

    Each stage goes to the right agent; gates run between them; and when a rule applies, the run surfaces an approval request and waits.

$ /agentic-slice "email users a digest of their items" orchestrator intake · scanning for gated actions… ⏸ HOLD rule 1 — sending on a user's behalf run paused · APPROVAL_REQUEST-1.md written waiting for an explicit yes… you approve ✓ recorded · APPROVAL_RECORD-1.md architect → engineer → qa → security → release ✓ all gates green · 0 retries

Evidence

Validated on live runs, not a slide.

The pipeline has carried slices to merged pull requests on the reference app—then built a second app from a one-paragraph brief, market research through to a shipped, tested service. Tiers 2 and 3, deterministic-first AI, a greenfield 0→1—and a security gate that stopped its own release.

The runs correct themselves—and sometimes their author. Security review caught a finished slice quietly listening on every network interface instead of loopback, reached a user’s data across the LAN to prove it, and sent the work back; the same flaw was then found and fixed in the older app it came from. Earlier, discovery caught a correctness trap before a line of code existed, and QA found a bug whose proposed fix Security then proved insufficient. A slice that blew its token budget didn’t get a quieter budget—the budget was re-derived from evidence and the one genuinely hot stage was flagged. And the two hardest tests still pass: shown an unsafe ask it refused at intake; shown an impossible one it bounded the failure and escalated—without weakening a gate.

Honest limits

Where it costs you, and where it isn’t proven.

The scorecard in this repo lists what isn’t validated, so this page should too.

  • It spends real tokens. A slice runs four to ten stages at roughly 70k–130k tokens each — a full greenfield build measured 947k. That is the price of every stage forming its own independent judgement, and it is exactly why the pipeline checks a budget before each step rather than reporting the damage after.
  • Small changes do not need this. Running a one-line fix through nine gated stages is theatre. The Engineering Manager compresses the pipeline for small slices and records why; reach for the full chain where being wrong is expensive, not by default.
  • Least-privilege binds conditionally. Per-role tool restrictions are generated correctly, but only take effect when the orchestrator session runs inside the product repo. Run it from elsewhere and you get capable agents with unrestricted tools — documented on the architecture page rather than buried.
  • Not yet proven: real-cloud deploy and live production SLOs, enterprise multi-tenancy, and a real model wired into a shipped feature. Each is listed as open in the validation matrix — none of them are claimed here.
