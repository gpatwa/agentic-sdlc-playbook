Architecture & data flow

A pipeline of narrow agents, gated end to end.

How the lifecycle is put together: the agent topology, the artefacts that flow between them, and the control loop that measures and budgets its own runs.

source agentic-sdlc-playbook ·reference apps stash-seed · streak-seed

The problem

One agent holding everything degrades.

A single general-purpose agent asked to “build the feature” holds the PRD, the design, the architecture, the code, and the QA notes in one context window — and degrades. This is the alternative: a pipeline of narrow agents, each with one job, passing artefacts to the next, gated by a control plane, with a human at the points that matter.

So the architecture here is not services and databases. It is an information-processing system:

  • Nodes are agents — one brief each.
  • Edges are artefacts — the data passed from one agent to the next.
  • Inputs are the product’s .agentic/ context plus a project pack, read by every agent.
  • Control plane is release gates plus human-approval rules, gating each transition.
  • Loop — Post-Launch feeds the Orchestrator, which starts the next slice.

    SEC -->|"findings"| REL["Release Manager"]
    REL -->|"ship"| PL["Post-Launch Learning"]
    PL -. "carry-forward" .-> O
    AG[(".agentic context + project pack")] -. "read first by every stage" .-> PM
    GATES{{"Release Gates + Human Approval Rules"}}
    ENG -. "impl gates" .-> GATES
    SEC -. "security gates" .-> GATES
    REL -. "confirms all gates" .-> GATES
  • A slice enters as a free-form human ask and leaves as a shipped, reviewed, learned-from change. The loop back from Post-Launch is what makes it a lifecycle rather than a line.
  • Each agent reads only its incoming artefact, the .agentic context, and the project pack — not the whole repo, not the prior conversation. That context discipline is why the role split saves tokens.
  • The Engineering Manager compresses the pipeline for small slices (skip Market Research, collapse design) and records why.
  • Overlay roles — Data Governance, AI Governance, Compliance, FinOps, Tech Writer, SRE, Customer Success — attach when an enterprise context is enabled. They are additive; a B2C MVP runs without them.
  • The control plane is not a stage — it gates transitions. An artefact cannot advance until its gate passes, and a fixed list of actions (send, deploy, destroy, new data processor) halts for a human.

Execution and the feedback loop

Views 1 and 2 describe the methodology. This is the part that actually runs — and it closes a loop: the playbook compiles into a product repo, runs there produce telemetry, and the telemetry changes the playbook.

    OUT -.->|"outliers become carry-forwards"| BR
    OUT -.->|"re-baselined budgets and SLOs"| PR
  • The playbook compiles. The installer turns briefs and protocols into a runnable pack inside the product repo, with per-role least-privilege tools. Caveat: those restrictions only bind when the Orchestrator session is rooted in the product repo, where the generated agents are discoverable.
  • Cost is governed before it is spent. A PreToolUse hook checks every agent spawn against the slice’s declared budget and asks the human when it would be exceeded. It fails open by design — a cost control must never block legitimate work. Release gates fail closed; convenience guards fail open.
  • Telemetry is data, not prose. Each run emits a machine-readable trace alongside the human-readable state file, and the analytics are rendered from it. Author once, render many — the views are never hand-maintained, so they cannot drift from the record.
  • The dotted return edges are the point. Detected outliers become carry-forwards that change briefs; measured cost re-baselines budgets and SLOs. That is what makes this a control loop rather than a pipeline with a dashboard bolted on.

Under the hood

Four properties make it work.

  1. Artefacts, not chat. Each agent’s only contract is the artefact it reads and the artefact it writes. It does not need the conversation that produced its input — which is what keeps every node’s context small.
  2. Gates fail closed. A failed gate sends the slice back to the owning stage, never forward. The gates encode failure modes that have bitten before: silent regression, approval bypass, logged secrets, runaway cost.
  3. The human is in the loop by rule, not by vibe. A small, fixed list of actions always stops for explicit approval. Everything else the agents are trusted to do within a slice.
  4. The system observes and governs itself. Runs emit telemetry; generated analytics flag their own outliers; budgets are checked before the spend, not reconciled after. When a measurement contradicts a target, the target is re-derived from evidence and the change is recorded — never quietly loosened to make a red thing green.
This began as a methodology rather than a running system, and Views 1–2 capture it that way. That is now only half the story: the execution layer compiles the methodology into a pack that really executes — generators, protocols, a hook, telemetry, analytics — which is what View 3 draws. There is still no deployment or container diagram, because the runtime is a developer machine and a product repo, not a fleet.
